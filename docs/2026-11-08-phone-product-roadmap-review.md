# 按手机使用逻辑管理 SIM 与通话：功能规划评审

日期：2026-11-08  
状态：评审与建议，尚未进入功能开发。  
代码基线：`feature/2026-11-08`，`10d69fd`；评审开始时工作区干净。  
输入：用户提供的 `feature-roadmap-20261108.md`；现有最终修复计划、功能审计和本地源码。  
上游核对范围：本地已有的指定提交对象，没有将本地远程引用视为 GitHub 实时最新版本。

用户本次原话：

> 如果按照一台手机的逻辑去管理这个卡和相关通话功能，应该可以从哪些方面进行功能补全和优化。你看看这个文件里面说的问题和功能有价值吗？应该如何开展。

## 1. 结论

原清单有价值，通信记录、短信会话、号码展示、诊断和统一静音都值得做。但它主要按文件和技术功能组织，适合作为候选清单，尚不适合作为直接开发顺序。

建议产品目标：把当前模块控制台逐步补成“在 Mac 上使用的电话与 SIM 管理器”。用户首先关心这张卡能否接打电话、有没有漏接、短信能否保存、当前使用哪张卡，以及出问题后怎么恢复。

应调整为以下顺序：

1. 先保证接打电话、提醒和设备恢复可靠，同时处理既有接口访问控制问题。
2. 建立按卡归属的本地通信存储，先解决短信落盘后再清理模块。
3. 做最近通话、未接来电、短信会话与轻量联系人，形成日常使用闭环。
4. 再补流量统计、套餐提醒、本地备份恢复和可选云盘快照。
5. 最后评估高级运营商业务、多模块和完整 SwiftUI 工作区。

保留本地已验证的电话与音频路径。上游能力按职责选择性适配，不整套替换通话服务。代码拆分随着相关功能发生，避免先进行全仓大重构。

本评审不替代 [最终修复计划](2026-11-07-final-repair-plan.md) 中仍未完成的认证、USB 生命周期、AT 事务和实机验收。

## 2. 核对发现与需纠正的判断

| 原清单判断 | 本次核对 | 对开发的影响 |
| --- | --- | --- |
| 本地完全没有通信历史 | 缺少持久化历史属实；但有内存通话状态和短信缓存。结束通话超过约 10 分钟后被清理，短信缓存最多 500 条 | 应称“缺少可靠、持久化的通信记录”，不能把现有状态与历史混为一谈 |
| 服务重启，短信就丢 | 内存缓存会丢；仍在模块上的短信可能重读。更严重的是 USB 轮询合并到内存后会自动清理 ME，尚无本地持久化确认 | 优先建立“落盘成功后才允许清理”的边界；现有内存缓存和模块清理组合存在数据丢失窗口 |
| Telegram 修复已完成 | `10d69fd` 增加连续失败计数与日志节流 | 日志降噪不能证明连接根因已修复，也不能证明 Bot 收命令和通知发送通过业务验收 |
| 没有备用通道，主通道失败直接丢通知 | 当前向所有已启用且配置完整的通道并行发送，并非单主通道模式 | 可增加送达状态、持久化重试、可选顺序降级；先定义与现有并发多通道的关系 |
| 原生开发被缺少 Swift 环境阻塞 | 本机实际有 Swift 6.1.2，目标为 Intel macOS；项目已有 Swift 状态栏与原生通话面板 | “必须等 MaVo 才能编 Swift”不成立。但未移植的 SwiftUI App 能否构建、ARM 实机能否运行仍需独立验证 |
| 把诊断工具移到 scripts 就能排除包扫描 | 目录改名本身不能保证 `go test ./...` 不发现 Go 包；留在 cmd 也不等于测试会拨号 | 工具保留有价值。先验证默认测试无硬件副作用，再决定构建边界，无需为目录名搬动 |
| D8 可直接展示丢包率与回声趋势 | 目前有样本、队列、丢弃、欠载、削波等计数；RTP 主要提供收发包数 | 音频样本丢弃不等于网络丢包率，AEC 开启不等于回声已消除；缺少的测量必须先实现 |
| 上游 TrafficHistory 可提供日/月统计 | 指定提交中的 Swift 结构只保留最近 36 个速率样本，并非日/月持久化账本 | 流量统计需新做服务端采样、持久化和计数重置处理，不能仅移植图表 |
| QNWINFO 两套解析可直接删一套 | 两处输出口径不同，一处仅返回网络名称，USB 路径还解析双工、频段和信道 | 统一语义并覆盖响应样本后再删除，不能按命令同名机械去重 |
| S1–S3 都应优先拆大文件 | 清单前文建议 SIP 整合前拆分，末尾又建议整合后拆分，存在顺序冲突 | 只做当前修改必需的同包拆分；大范围整理放在业务职责稳定后 |

额外说明：原清单把部分小项放在“P1 小件”阶段，但正文标为 P2。建议统一使用本报告的阶段及验收条件；工时描述只能作为初估，不把“上游已有”当成可直接交付。

## 3. 手机使用逻辑下的功能结构

建议主导航围绕“电话、信息、联系人、SIM 与网络、设置”。底层保留 AT、eSIM、GNSS、任务和 MCP，放到相应工作区或高级入口。先补业务闭环，不要求立即重做全部界面。

| 范围 | 用户需要完成的事 | 建议补全 | 优先级 |
| --- | --- | --- | --- |
| SIM 身份 | 知道当前用哪张卡、哪个号码 | 卡片别名、颜色、本机号码及来源、ICCID 脱敏、活动 Profile、卡状态和能力 | P0 数据基础，P1 展示 |
| 电话 | 看到来电并可靠接通、连续使用 | 统一状态、明显提醒、拒接/取消区分、通话时长、DTMF、麦克风/输出控制、音频设备选择 | P0 |
| 最近通话 | 找到漏接号码并回拨 | 全部/未接、呼入/呼出、结束原因、按卡筛选、回拨、发短信、保存联系人 | P1 |
| 信息 | 找到和回复短信 | 持久化收发记录、号码会话、未读、草稿、搜索、分页、长短信与发送状态 | P0 存储，P1 体验 |
| 联系人 | 按姓名拨号和识别来电 | 本地轻量联系人、多号码、号码匹配、收藏、从历史新建 | P1 |
| 来电管理 | 不漏接、不重复响铃 | 后台原生提醒、未接角标、统一铃声与静音、免打扰、可选黑名单 | P0 提醒，P1 静音，P2 规则 |
| 网络与套餐 | 判断能否上网、还可用多少 | APN、漫游状态、可信的联网检测、周期流量、手动套餐与提醒 | P1–P2 |
| 系统与恢复 | 插上就能用、出错能恢复 | 首次检查、权限状态、重连、睡眠唤醒、重启恢复、脱敏诊断导出 | P0 |
| 数据管理 | 更新与迁移后记录仍在 | 本地备份/恢复、保留期限、删除范围、可选云盘快照、备份隐私设置 | P1–P2 |

### 卡片身份必须先于记录筛选

建议引入内部 `subscription_id` 作为卡片/Profile 的稳定引用，同时保留读到的 ICCID、设备标识、连接代次和身份来源。

- ICCID 用于识别订阅/Profile；IMEI 用于识别模块；EID 用于识别 eUICC。三个层级不能混用。
- 手机号是可空、可更正的属性，不作为卡片或通信记录主键。
- 号码区分 SIM 自动读取、用户备注、未知；不把备注显示成运营商已验证的结果。
- 每次通话/短信事件保存当时的卡身份快照，不能查历史时用“当前卡”反填全部记录。
- 读不到原始归属的模块旧短信保持“归属未知”。换卡、Profile 切换和断连期间的记录同样保留不确定性。
- 联系人保存原始号码与用于比较的标准化号码。地区不明确时不盲目补国家码，也不能仅按尾号合并身份。

### 电话状态与历史状态分开

现有代码已有 `dialing/ringing/active/ended/failed/missed`，并具备 DTMF 和本机静音控制，应该补齐行为与展示，而不是再建一套同类实现。

需要补充的是接通中、结束中等操作反馈，以及明确的结束原因。主动拒接、对方取消、未接超时、无网络、忙线、媒体失败和设备断开不应全部记成“未接”。

通话时长从确认接通起算；“模块已接通”和“媒体已就绪”分别可见。挂断后只更新同一条历史，号码晚到也只更新该通话。

## 5. 分阶段开展与交付边界

### 阶段 A：把电话和提醒做可靠

对应既有修复计划步骤 05–09、D7、D8、O1 与 O5。

- 固定当前可用版本和电话基线，确认原生、网页与 SIP 入口的唯一状态和媒体所有权。
- 完善来电、号码晚到、主叫取消、拒接、接听失败、连续通话的反馈。
- 检查 USB 重连、AT 竞争和长扫描；新查询与初始化不能拖延接听。
- 提供轻量初始化诊断：卡是否就绪、注册状态、权限、音频设备、语音路由和可恢复原因。
- 来电由服务端持续检测；网页隐藏可降低展示轮询，不能停掉唯一来电检测链。
- 完善现有访问控制。普通接打电话保持顺畅，不给每次操作额外增加确认弹窗。

交付标准：连续呼入 10 次、呼出 10 次，混合接听、拒接和对方取消，不出现残留通话、双重响铃或第二次无声；另完成耳机/扬声器各一组及至少一次 10 分钟通话。首声、接听响应分段记录全部样本，报告中位数与最差值。目标值在测得基线后确定，不能预先承诺运营商侧时延。

这些是真实设备验收计划，本次没有执行。

### 阶段 B：本地记录与卡身份

对应 D1 的本地部分、D4，并支撑 D2、D3、D11。

- 建立订阅身份、通信记录、短信及发送尝试的存储边界；数据库方案优先评估 SQLite。
- 为数据库增加版本迁移、唯一约束、时间与排序字段、错误返回和回退说明。
- 通话通过现有状态事件更新历史，不另起一套每 3 秒查询 CLCC 的独立监视器。
- 接收短信持久化成功后再清理模块，存储失败保留模块数据并显示故障；清理范围必须与已保存数据对应。
- 为长短信保存重组状态和去重依据。不能只依赖内存或“号码+正文”合并，避免误吞合法重复短信。
- 发件箱保存正文、分段及尝试状态，区分已提交、已送达、失败和结果不确定。无法证明未发送时禁止自动补发。
- 应用重启后未结束通话标记为中断/结果未知，不能凭空补结束时间或通话时长。

交付标准：重启保留记录；重复轮询不新增重复记录；合法重复短信不被误删；磁盘满/只读时不清理未保存短信；A 卡换 B 卡不串归属；模块旧短信无法确认归属时显示未知。

### 阶段 C：补齐手机日常使用闭环

对应 D2、O5，以及新增的最近通话与联系人。

- 电话：最近记录、未接筛选、角标、一键回拨、发短信、保存联系人。
- 信息：按号码会话、未读、草稿、搜索、分页、分段发送与送达状态、导出。
- 联系人：先做本地姓名、多号码、收藏与号码识别；系统通讯录集成和批量导入后做。
- 设置：铃声、音量、单次静音、免打扰；保留明确的视觉来电与未接记录。
- 统一联系人、短信和电话的号码匹配，保留原始号码用于展示与追溯。

交付标准：从未接记录回拨并挂断、从短信会话拨号、未知号码保存联系人后更新展示、重启保留草稿和未读状态；网页与原生端状态一致。

### 阶段 D：网络、流量与恢复

对应 D3、D5、D6、O2，D10 可按实际运营商支持情况插入。

- 联网检测区分接口存在、获得地址、路由、DNS 和公网；记录检测走的出口。
- 流量采样在后台服务进行，关闭页面仍统计；切卡、接口变化、计数归零、睡眠与服务重启建立新采样区间。
- 无法采样的时间保留缺口，不用插值冒充实际流量。账期、限额、余额允许用户手动维护并注明来源。
- 恢复从无损刷新开始；涉及网卡重建、模式切换或模块重启时，先检查通话和 eSIM 操作占用。

交付标准：Wi-Fi 在线而 4G 不通时不能报 4G 正常；计数重置不出现负数或巨额流量；通话中不允许触发破坏当前通话的恢复动作。

### 阶段 E：备份、迁移与进阶功能

对应 D1 的备份部分、D11、D12；D9 保持独立后续项目。

- 先提供本地一致性快照、恢复预检和恢复前备份，再增加用户主动开启的云盘目录备份。
- 不把正在写入的数据库直接放到同步目录；发布完成的快照。“已写入同步目录”与“已上传云端”分别表达。
- 定义备份是否包含短信正文、是否加密、保留周期，以及删除记录会不会被旧备份恢复。
- MCP 新工具继续只读，按授权范围返回内容。
- 原生工作区逐页替换展示，继续复用现有服务，不再引入第二个服务、来电检测器或音频管理者。

交付标准：快照校验通过；损坏备份不覆盖现有记录；重复导入无重复；恢复失败有回退；Intel/ARM 构建与硬件验收分别记录。

## 6. 上游移植的具体原则

已核对原清单引用的 `612c2f6`、`ed5092c`、`5de69f9`、`a55e577`、`4be65e2` 和 `45622dc`。这些指定提交确实包含相关实现，但不能因此认定全部适合直接合并。

1. **优先复用能力与测试**：历史表结构、迁移、快照发布、CNUM 解析、网络诊断样本。
2. **适配现有事件与数据目录**：上游历史依赖 `voiceCall`、`audioMu` 和独立 CLCC 轮询，本地已有 SIP 状态事件与音频桥；需要适配，不能直接装配两套控制链。
3. **重新检查性能**：上游历史启动时加载全部记录，保存时重新编码内存历史；不能因用了 SQLite 就认定支持长期大量数据。目标实现应支持增量写入和数据库分页。
4. **重新检查安全**：上游备份操作使用特定 Header 与无 Origin 检查，这不能替代本地接口认证；路径选择与恢复权限纳入统一控制。
5. **避免增加 AT 压力**：CNUM、卡身份、诊断与历史不能各自频繁查询模块。使用已确认的连接代次及身份快照，变化时失效。
6. **拆开提交与验收**：存储、号码、网络、界面、备份分别形成可回退单元。数据库驱动的无 cgo 与双架构能力必须在本仓库实际构建验证。

当前本地引用下相对 `upstream/main` 为 7 ahead / 11 behind，只用于说明分叉，不能据此决定直接合并全部上游。

## 7. 需探测后才能承诺的手机能力

以下是候选需求，不是已确认支持的功能：

- SIM PIN/PUK 输入、修改与剩余尝试次数：先探测只读能力，不自动猜测或反复提交。
- 呼叫等待、保持、切换、转移、主叫隐藏、会议：分别确认模块固件和运营商支持，再定义交互；不可仅看到标准 AT 命令就承诺可用。
- 黑名单：先明确是本机静音、拒接还是仅隐藏提醒；不保证对方听到固定提示。
- 短信送达报告：没有报告时保持已提交/待确认，不能显示为已读或已送达。
- 来电身份：区分号码尚未到达、未提供和读取失败；本机号码读取与主叫号码显示是两条独立链路。
- 呼叫与上网并行、VoLTE、漫游、USSD 余额：逐固件和卡验证，不以 IMS 单次读数替代实拨与联网验收。

本次额外尝试检索 Quectel 官方 AT 手册，未取得可用于核实这些能力的页面。因此以上能力保持“待探测”，没有用外部通用资料替代当前硬件验证。

## 8. 建议首先推进的交付包

建议从“可靠电话 + 本地通信记录”开始。开发时可以分别提交，但验收统一覆盖：

1. 当前接打电话、来电提醒和连续通话的可重复基线。
2. 按卡身份保存短信与通话；解决内存接收后即清理模块的数据丢失窗口。
3. 最近通话和未接记录，可直接回拨。
4. 短信会话、搜索与明确的发送状态。
5. 号码读取/备注和初始化诊断。

联系人可以在这些基础稳定后紧接着做。云盘备份、大文件重构、多模块和整套 SwiftUI 移植不作为第一包的前置条件。

每个交付点记录：基线提交、变更、自动测试、实机结果、未验证项和回退方式。模拟测试、编译通过、设备读取和真实业务通过分开记录；测试数据不包含真实短信或凭据。
