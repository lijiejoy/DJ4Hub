# 项目修复方案独立评审

日期：2026-11-07

评审对象：[项目问题全面分析与修复方案](2026-11-07-project-issue-review.md)
关联材料：[现有功能梳理报告](2026-11-07-feature-audit.md)

## 一、结论

**判断：问题清单整体有价值，修复方向大体合理；建议修改后采纳，不建议直接按照原文“四批顺序”执行。**

安全、USB 生命周期、AT 多命令序列、后台退出和任务持久化确实值得优先处理。但原方案混合了已确认问题、尚未验证的攻击效果、错误的修复方法和较低优先级的整理工作。直接实施可能留下密钥泄漏、引入锁等待甚至死锁，并在合并上游时破坏已经验证过的通话能力。

最需要修改的地方：

1. 仓库目前是“本地提交落后、工作区有大量改动”，不能直接称为提交历史已分叉。先形成可恢复快照，但不要把完整合并上游设成所有修复的前置条件。
2. 上游和本地各自有电话、音频及来电提醒实现。必须先明确统一的设备控制和通话状态归属，再设计整合，而非只解决七个文件的文本冲突。
3. `url.URL.Redacted()` 不适合这里的密钥脱敏；SMTP 的错误检查和超时需要补齐，但 Bark 已有请求上下文超时。
4. USB 生命周期锁与 AT 会话锁应分开设计；不能通过“全程持一把锁”或无限扩大串行范围解决所有问题。
5. 测试应随高风险修复同步交付，不能放到最后一批再补。构建通过也不能证明真实双向通话、回声、延时、来电提醒均已修复。

本次只新增评审文档，未修改业务代码、提交或合并 Git 历史，也未重启服务、拨号或执行设备写操作。

## 二、评审依据与边界

本评审核对了本地工作区中的相关处理器、USB 实现、测试、构建配置、发行说明，以及本地缓存的 `origin/main` 中的电话和音频实现。关键代码入口见各节及逐项表。

本轮直接核实：

- `git rev-list --left-right --count HEAD...origin/main` 返回 `0 11`；本地 HEAD 为 `db8737a`，缓存的 `origin/main` 为 `3914cd6`。本轮未拉取远端，不能据此声称掌握远端最新状态。
- 工作区仍有大量已修改和未跟踪文件；文件数量会变化，原文的数量应视作记录时的快照。
- 本机 `go doc net/url.URL.Redacted` 明确说明只隐藏 `u.User` 中的密码。
- 本机 `go doc net/http.NewRequestWithContext` 明确说明请求上下文覆盖获取连接、发送请求、读取响应头和响应体。

本轮没有重跑全量测试、竞争检测或无 cgo 构建，也没有复现浏览器攻击、SMTP 故障或 USB 并发故障。原方案列出的测试通过结果属于原方案的验证记录，不是本评审新产生的测试结果。以下“代码确认”不等于“故障已实机复现”。

## 三、执行前必须修正的建议

### 1. 仓库保全合理，但“必然七个冲突、提交零风险、必须先合并”不合理

`0 ahead / 11 behind` 表明当前提交历史允许快进。真正阻碍直接更新的是未提交改动及未跟踪文件可能被覆盖。先提交本地改动后，才可能形成需要合并或变基的分叉历史。

七个重叠文件是冲突风险范围，不代表必然产生七个文本冲突。即便 Git 自动合并成功，也不能排除功能冲突。

更关键的是，上游包含：

- `cmd/dj4ghub-macos/phone.go`、`module_audio.go`、`alerts.go` 和通信历史存储；
- `apps/hub-macos/` 原生应用及音频、来电提醒；
- `web/phone.js`、`history.js`、`alerts.js`。

本地则已有 [SIP 控制](../cmd/dj4ghub-macos/sip_handlers.go)、`internal/sip/`、[独立来电窗口控制](../cmd/dj4ghub-macos/call_alerts.go) 等实现。双方会操作同一模块、音频设备和来电状态。整合前应确定谁负责拨号/接听/挂断、音频启动与释放、来电去重和通话记录，避免一次操作触发两条控制链、两个窗口或两个音频会话。

建议先显式选择源码和文档形成可恢复快照，覆盖未跟踪源码；不能仅保存 `git diff`。检查二进制、个人脚本和 `.zwork/`，避免直接全部暂存。原文建议的八个主题之间有编译依赖，不应承诺每个拆分提交都可构建。可以先保全完整工作快照，再整理逻辑提交。

SMTP 崩溃、密钥错误回显等局部修复可以在保全后的本地分支先做，随后纳入整合，不必等待大规模合并完成。

### 2. 脱敏方法必须重写

在 [通知处理器](../cmd/dj4ghub-macos/notify_handlers.go) 中：

- `telegramAPIURL` 把 token 放在 URL 路径；
- `sendBark` 把推送密钥、标题和正文放在 URL 路径；
- 飞书 webhook 密钥也可能位于路径，其他服务还可能使用查询参数签名；
- `recordNotifyResult` 直接保存 `err.Error()`，发送工作协程也直接记录错误。

`URL.Redacted()` 只隐藏 `https://user:password@host/` 中的密码，不会隐藏上述路径和查询参数。以它作为核心修复，会造成“看似脱敏、实际仍泄漏”。

应优先生成结构化安全错误，只保留通道、阶段、错误类型和状态码，不直接输出请求 URL、响应正文或嵌套错误全文。确需保留的内容再按通道规则过滤路径密钥、查询签名、已配置的秘密及消息正文，并在日志和状态记录入口增加兜底。

原文还把两条传播链混为一条：`getUpdates` 失败由 `telegramBotLoop` 写日志；发送失败则通过 `sendToChannel` → `recordNotifyResult` 进入状态和通知记录。两条链都要覆盖，但不能声称轮询错误必然经过 `recordNotifyResult`。

若确认真实密钥已经进入日志，应安排轮换和历史副本处理；只遮住今后的 API 响应不能消除旧泄漏。本评审不展示或读取真实密钥。

### 3. SMTP 问题成立，Bark“没有超时”的判断不成立

`sendEmail` 的 SSL 分支未检查 `smtp.NewClient` 的错误，后续使用空客户端可导致 panic。非 SSL 分支使用 `smtp.Dial`，没有完整的上下文取消和连接读写期限；STARTTLS 错误也被忽略。这些修复应优先实施。

需要修正具体方案：

- 检查 `smtp.NewClient` 错误，并关闭失败连接。
- 明确 TLS 策略：要求 TLS 时，服务器不支持或握手失败都应返回错误。不能把“忽略握手失败”直接等同于“已经成功以明文投递”；实际投递效果本轮未验证。
- 连接建立使用带上下文的拨号，SMTP 欢迎语、握手及后续读写也需要期限；取消时应能终止阻塞操作。
- `sendNotify` 为每个通道另启工作协程。仅在外层加 `recover` 抓不到子协程的 panic；兜底应放在各工作协程边界，且不能替代正常错误检查。

另一方面，`sendToChannel` 已创建 `notifySendTimeout` 上下文，`sendBark` 使用 `NewRequestWithContext`。不能因为 `http.DefaultClient.Timeout` 为零就断言这条调用链没有超时。独立带超时客户端可以作为防御性改进，但不应列为已确认的无限等待漏洞。

### 4. USB 并发问题成立，但应采用分层控制

[main.go](../cmd/dj4ghub-macos/main.go) 的 `ensureUSBAT` 存在无锁检查、打开、写回；断连时还会修改设备、退避和发现状态。相关访问缺少统一同步，风险成立。

不过，[usbat_darwin.go](../cmd/dj4ghub-macos/usbat_darwin.go) 中 `Close` 和 `Command` 都持有 `u.mu`，并检查关闭后的句柄。因此不能仅根据应用层指针竞争，就把这两条路径定性为已经证实的底层 C 句柄释放后使用。

建议至少区分：

- **生命周期同步**：保证只有一个打开者；调用方取得稳定设备引用；旧连接的迟到错误只能使旧连接失效，不能清掉刚安装的新连接。使用连接代次或引用比较处理这一点。
- **AT 事务调度**：保证依赖同一模块状态的必要命令序列不被插入，同时限制扫描等耗时任务对接听、挂断和来电事件处理的阻塞。

生命周期锁不应跨慢速设备操作及可能回调同一管理器的初始化过程长期持有。会话接口需要可在锁内使用、不重复获取同一锁的执行器，避免会话调用 `runATCommand` 后递归加锁。

原文所称“粗粒度串行化全部 AT 对话”只能作为受限过渡方案，不能当最终目标：现有单条命令已经串行，长扫描再扩大锁范围可能进一步拖慢接听。

另外，`pkg/smscodec/reassembler.go` 本身有互斥保护；需要处理的是应用层重组器指针的懒初始化。不要扩大为“重组器全部无锁”。也不应声称任意信号/GNSS 查询都会改变短信存储，应围绕实际更改 CPMS、CMGF 等状态的交错设计测试。

### 5. 安全入口需定义兼容性，不能用一个头代替认证

未见统一 API 认证及 Host/Origin 防护，且 JSON 解码未限制内容类型，足以支持“应修复”的判断。但跨源请求及 DNS rebinding 在具体浏览器上的效果还受本地网络访问权限、预检和网络环境影响；本轮没有复现，原文“恶意网页两个请求即可完成”的说法过于确定。

落地方案应写清：

- 校验实际配置的 Host 和端口，包含所支持的 IPv6 情况；覆盖静态入口及 API，不接受任意域名后缀或未经信任的转发头。
- 区分浏览器同源请求、无 Origin 的命令行请求及合法本地客户端。`Sec-Fetch-Site` 是辅助信息，不能单独作为认证。
- 自定义头仅能改变浏览器请求条件；要叫“token 认证”，必须定义不可预测凭据的生成、发放、存储、轮换及读写接口范围。
- 保持 MCP Bearer 认证、网页首屏及轮询、原生应用和合法本地工具可用。不能为简化中间件而让这些入口全部失效。
- SIP 默认回环合理；是否禁止用户明确启用局域网访问是产品决策。API 配置权限与 SIP 网络暴露是两个需要分别控制的边界。

Host/Origin 防护不能阻止所有本地恶意进程；二次确认也不能替代身份认证。不建议给每一次正常拨号都增加系统确认。

### 6. AT 校验、测试工具迁移等建议应避免无效或破坏性修改

内嵌 CR/LF 的 AT 命令应**拒绝**，不要静默剥离后继续执行，以免改变用户指令含义。应区分 AT 命令行与短信提示模式的合法后续载荷；控制台原本是调试工具，不能未经设计就用笼统白名单削掉其正常用途。

把 Go 工具从 `cmd/` 移到普通 `scripts/` 子目录，不会自动使它退出 `go test ./...` 的包发现范围。`go test` 会编译这个 `main` 包，但不会因此执行其 `main()`、自动拨号。该工具对音频诊断仍有价值，保留并说明用途是合理选择；若采用构建标签，应同时验证对应启动方式。

## 五、建议的执行顺序

| 阶段 | 工作 | 完成条件 |

## 六、关键验收条件

### 安全与通知

- 使用假 token、假验证码及本地模拟服务，覆盖连接失败、超时、非成功响应、响应正文回显秘密和畸形 URL；检查日志、`last_error` 与通知记录均无秘密或消息正文。
- SMTP 模拟欢迎语失败、STARTTLS 不支持/握手失败、读写停滞及取消；所有工作协程应返回可理解错误，服务继续运行。
- HTTP 覆盖允许/不允许的 Host、端口、Origin、预检、text/plain 写请求、缺失/错误凭据，以及 IPv6（若支持）。
- 正向验证网页首屏和轮询、MCP Bearer、本地原生应用、合法命令行客户端；不只检查恶意请求被拒绝。
- 对 AT 命令行中的 CR/LF 及非法控制字节返回错误，提示模式合法载荷保持可用。

### USB、任务与关闭

- 用可控设备替身并发触发打开、断连和重连：同一代只打开一次；旧请求晚返回失败后，新设备仍有效；关闭后调用可控失败。
- 验证 CPMS/CMGF 等状态相关命令不会交错；扫描和短信事务期间测试接听/挂断的等待上限，并覆盖超时或取消。
- 配合真实执行上述路径的测试运行 `-race`；不能把单独增加命令当作并发问题已解决。
- 模拟任务执行前、执行后但落盘前退出，以及磁盘写入失败。收费动作结果不确定时不自动重发，并提供可见状态。
- 所有后台循环和已启动工作协程能响应取消，在约定期限内结束，不再继续发通知或操作设备。

### 电话与音频

合并前后使用同一设备和音频设置记录对照，分别检查：来电显示号码及后补更新、提醒去重、接听/拒接/对端挂断、双向音频、回声、首个有效声音时间、连续通话及 USB 重连。

原方案缺少语音质量的可比较基线。应先记录当前表现，再约定首声等待、往返延迟等目标；回声和音质还需同一场景的听感记录，不能仅凭“存在音频数据”判定通过。自动测试应使用替身或合成音频，真实拨号安排在明确的联调窗口内。

## 七、最终建议

保留原方案作为问题清单，将本评审中的纠正项、执行顺序和验收条件补入实施计划后再推进。优先保护凭据和服务稳定性、修正影响电话响应的并发路径；上游整合采用单独验证的步骤，文件拆分和清理放在行为稳定之后。

本评审支持继续修复，但不支持以“全量测试通过”“一个中间件封住全部问题”或“文本冲突已解决”作为功能完整、安全完成或通话体验达标的证明。
