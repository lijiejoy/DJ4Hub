# 2026-11-08：4G 上网模式无法给电脑提供网络

## 结论

本机已恢复 4G 数据共享。故障时模块处于 ECM 上网模式，蜂窝数据上下文已激活，但 macOS 的 Baiwang 网卡没有获得有效 IPv4 DHCP 租约和网关。重新申请地址、停用再启用网卡，以及临时停止应用服务，均未恢复租约；模块软重启后恢复。

因此，故障范围收敛到模块与 macOS 之间的数据共享／地址分配链路。尚未证明最初由固件、USB 重枚举、驱动或其他具体事件触发，不能仅凭重启有效认定是固件 DHCP 进程崩溃。

## 排查记录

| 检查 | 故障时结果 |
| --- | --- |
| macOS 识别设备 | Baiwang，接口 `en15`，链路 active |
| 上网模式 | `AT+QCFG="usbnet"` 返回 `1`，USB 描述包含 ECM 控制和数据接口 |
| 蜂窝数据 | `cmnet` 数据上下文激活，模块取得运营商 IPv4、IPv6 地址 |
| 主机 IPv4 | `169.254.*` 自分配地址，无 IPv4 网关 |
| DHCP | `ipconfig getpacket en15` 无有效租约 |
| 主机 IPv6 | 存在全局地址和接口限定的默认路由，但两次指定网卡的外网 HTTPS 连接均超时 |
| 普通上网出口 | Wi-Fi；电脑原有联网成功不能证明 4G 可用 |
| 应用网络显示 | `/api/network/local` 错误返回 `en6`，实际模块网卡为 `en15` |

日志在 15:50:44 记录过 USB 连接丢失并重新打开，但目前没有足够证据证明该事件就是本次上网故障的起点。

## 恢复步骤与实测

1. 对 Baiwang 网络服务重新申请 DHCP，未恢复。
2. 确认无活动通话后，临时停止应用后台服务，停用再启用 Baiwang 网卡并重新申请 DHCP，仍未获得租约；随后恢复应用服务。
3. 再次确认无活动通话，通过已有接口执行一次 `AT+CFUN=1,1` 软重启模块，保留上网模式、APN 和其他持久设置。
4. 模块重新枚举后，电脑收到 DHCP ACK，获得 `192.168.225.25/24`、网关及 DNS `192.168.225.1`。
5. 指定 `en15` 并绕过代理验证外网：IPv4 HTTP 返回 301，百度 HTTPS 返回 200；请求本地地址均为 `192.168.225.25`。
6. 指定该网卡地址向模块 DNS 查询，成功返回域名 A 记录。后台健康检查为正常。

这些结果证明恢复后的请求经过 4G 网卡。未调整全局网络服务优先级，电脑日常默认出口仍可优先选择 Wi-Fi。

## 代码中另一个已确认的问题

`cmd/dj4ghub-macos/network_handlers.go` 的 `selectUSBTrafficInterface` 把第一个 active 且不是 `en0` 的以太网接口作为模块网卡。本机 `en6` 满足这一条件，但它不是 Baiwang 网卡，导致网络显示、流量统计和相关诊断可能选错对象。

`hasLikelyUSBNetworkInterface` 和 `check4GRoute` 也使用类似假设。Wi-Fi 的接口名不能普遍假设为 `en0`，其他 USB 或内建以太网也不能直接视为 4G 网卡。

本次仅排查和恢复运行环境，未修改或部署上述网络识别代码。后续应将模块 USB 身份与实际网络接口绑定，明确区分：设备存在、链路连接、有效地址、网关、DNS、指定接口外网连通性，以及当前默认出口。
