# 连续通话与麦克风授权修复记录

日期：2026-11-07。

## 连续通话故障

用户反馈：首次接通快，但挂断后再次接听显示通话中，实际没有声音。

排查发现，模块侧语音进程虽然仍存活、PCM 显示 RUNNING，但硬件读写位置不再推进。
失败通话中电脑麦克风有数据，模块输入和电脑扬声器没有非零数据。
因此不能用“进程存活、PCM 正在运行”证明上一通留下的路由仍可供下一通使用。

修复后，每个媒体会话都重新建立本应用拥有的 DSP 路由。仍复用独立 ADB 服务、
已验证的资源和校准，避免每通完整传输和初始化；仅结束经 PID、启动时间与路径验证
属于本应用的进程，不结束其他程序的进程。检查失败时走完整恢复路径。

硬件准备测试验证相邻会话的路由进程身份不同，电脑音频在接听前没有采集或播放。
两次准备分别为 2.192 秒、2.221 秒；原始完整准备为 7.359 秒。
之前约 1.7 秒的直接复用方案已撤回，这些时间不等同于手机接通到听见声音的时间。

## 麦克风授权

首次权限申请提前到已启用的通话服务启动阶段；申请权限本身不打开麦克风音频流。
启动与通话共享串行授权检查，同一进程最多发起一次首次申请，避免并发或超时后
每通重复申请。已获系统授权时直接继续，不再次请求授权。

每次使用仍读取系统权限：用户撤销后阻止采集，用户在系统设置重新允许后立即生效。
应用不会以本地配置伪造或覆盖系统授权。

系统保留授权且程序身份不变时，无需每通确认。当前安装的程序没有正式代码签名，
替换构建后系统仍可能要求重新授权；无法仅通过缓存实现跨版本的永久授权。
本轮替换后的服务最初报告 `not_determined`，随后已确认系统状态变为 `authorized`。
获得授权后，两通连续测试期间及挂断后均保持已授权，无需每通再次发起申请。
若未来被撤销，可在“系统设置 > 隐私与安全性 > 麦克风”中重新允许应用或其启动程序。
